# container-gateway 双节点压测报告

版本：container-gateway 1.0.0
日期：2026-11-04
测试环境：local + w1
镜像：sandbox-runtime:2026.1104
报告状态：已确认（历史记录）

> 背景：网关可管理多台 Docker 机器；“节点池”指可调度的节点组。本报告验证加入第二台节点后，容量、调度分布与吞吐的变化。
>
> 术语速查：TFS 是当时的内部工单 / 代码系统；SSE 是服务器持续推送事件的 HTTP 格式；tick 指一次流消息；activeStreams 指当前活跃流数；fd 指文件描述符；copy-up 指首次写入时从镜像层复制到可写卷；force destroy 指强制删除容器；rps 是每秒请求数；p50 / p95 是 50% / 95% 分位延迟。

---

## 0. 结论摘要

| 结论 | 数据 |
|---|---|
| 容器容量 | 单节点 30 个成功；双节点 59 个成功（池容量 60，被 1 个业务容器占 1 位） |
| 单节点上限 | 严格生效：60 并发时 30 成功 / 30 个 503 |
| 创建延迟 | 单节点 p50 798ms；双节点 p50 661ms |
| 节点分布 | 创建 local 30 / w1 29；CPU 压测 8 / 8；exec 60 / 58 |
| 轻量 exec | 单节点 62.9 rps；双节点 62.4 rps，基本不提升 |
| CPU-bound | 单节点 7.05s；双节点 3.63s，加速 1.94x |
| SSE 流 | 200/节点：400 条并发全部 200，activeStreams 200/200，结束后归零 |
| 销毁 | 单节点 p50 355ms；双节点 p50 187ms |

总体判断：

1. 加节点显著提升容量与 CPU 型任务吞吐，CPU-bound 接近线性（1.94x）。
2. 轻量 echo exec 的瓶颈在网关请求链路与 Docker exec 往返，不在节点数量；继续加节点不会提升这类 QPS。
3. 调度“创建即占位”生效：单节点 30 上限不再被并发绕过，双节点分布接近 50/50。
4. 镜像瘦身 + 调度占位后，远程创建从改造前并发 p50 约 9.7s 降到 0.66s。
5. 流式容量已验证：200 流/节点、连接池 600，400 条并发 SSE 全部成功，资源可回收。

## 1. 测试目标与范围

### 1.1 目标

- 验证加入 w1 后，单节点并发上限是否被正确执行。
- 对比单节点与双节点在容器容量、轻量 exec、CPU 型任务上的差异。
- 判断 w1 是否获得合理比例的请求。
- 评估网关链路连接复用的优化空间。

### 1.2 范围

- 覆盖：创建、销毁、轻量 exec、CPU-bound exec、SSE 并发、节点分布。
- 不覆盖：长时间稳定性、节点故障切换（另行演练）、3 节点以上线性度、文件/反代专项压测、多网关、SSE 高输出场景。

## 3. 测试方法

### 3.1 客户端

- Python 多线程 + urllib。
- 每次请求新建 TCP 连接（未使用客户端连接池）。
- 因此本文的轻量 exec/QPS 是偏低的下界；连接复用后会更高。

### 3.2 单节点基线

- 在网关侧用 iptables REJECT 到 w1 的流量。
- 等待 w1 在 /healthz 中变为 DOWN（约 5-10 秒）。
- 仅使用 local 执行相同的创建/exec/destroy 负载。
- 测试结束后解除阻断，确认 w1 恢复 UP。
- 注意：基线期间 w1 上已有业务容器会短暂不可访问，测试后已恢复。

### 3.3 双节点

- 解除阻断，确认 local、w1 均 UP。
- 执行同样的负载，记录每个容器的 nodeId。

### 3.4 场景参数

| 场景 | 容器规格 | 数量/并发 | 负载 |
|---|---|---|---|
| 容量/调度 | 0.1 CPU / 128MB | 60 个创建，15 并发 | 创建后立即 2 轮 echo exec，再并发销毁 |
| 轻量 exec | 同上 | 60 个容器 | 每容器 2 次 echo ok |
| CPU-bound | 1 CPU / 512MB | 16 个容器，16 并发 exec | 每容器 SHA-256 3000 × 1MB = 3GB |
| SSE 并发 | 0.1 CPU / 128MB | 40 个容器，400 条流（10/容器） | 每流 10 次 tick，持有 8 秒 |
| 销毁 | 同上 | 10 并发 | force destroy |

CPU 负载使用 Python hashlib，单容器耗时约 2-3 秒（空闲时），用于放大 CPU 调度差异。

## 4. 测试结果

### 4.1 容器容量与创建

| 指标 | 单节点 | 双节点 |
|---|---|---|
| 创建成功 | 30 | 59 |
| 创建失败 | 30 × 503 | 1 × 503（容量已满） |
| 分布 | local 30 | local 30 / w1 29 |
| p50 | 798ms | 661ms |
| p95 | 922ms | 1058ms |
| max | 931ms | 1067ms |
| 销毁 p50 | 355ms | 187ms |

说明：双节点测试时已有 1 个业务容器，双节点总容量 60，因此成功 59 个；503 是预期的容量保护，不是故障。

### 4.2 轻量 exec（echo）

| 指标 | 单节点 | 双节点 |
|---|---|---|
| exec 次数 | 60 | 118 |
| 总耗时 | 0.95s | 1.89s |
| 吞吐 | 62.9 rps | 62.4 rps |
| p50 | 214ms | 216ms |
| p95 | 303ms | 379ms |
| 分布 | local 60 | local 60 / w1 58 |

结论：轻量 exec 吞吐基本不随节点数提升。w1 承担约 49% 请求，说明路由分布合理；瓶颈在网关请求链路和 Docker exec 多次往返。

### 4.3 CPU-bound

| 指标 | 单节点 | 双节点 |
|---|---|---|
| 容器数 / 分布 | 16 / local 16 | 16 / local 8 + w1 8 |
| 总耗时 | 7.05s | 3.63s |
| exec 吞吐 | 2.27 次/s | 4.41 次/s |
| 计算吞吐 | 6.65 GB/s | 12.91 GB/s |
| p50 | 6593ms | 3475ms |
| p95 | 7035ms | 3627ms |
| 销毁 p50 | 493ms | 237ms |

加速比：1.94x。单节点 16 个 1 CPU 任务在 8 核上 2 倍超卖；双节点 8+8 正好一台 8 核跑 8 个任务，接近线性。

### 4.4 请求分布

| 场景 | local | w1 | 判断 |
|---|---|---|---|
| 容量创建 | 30 | 29 | 接近 50/50 |
| 轻量 exec | 60 | 58 | 约 49% 在 w1 |
| CPU exec | 8 | 8 | 完全均衡 |
| SSE 流 | 200 | 200 | 每节点 200 并发，符合配置上限 |
| 单节点基线 | 30 | 0 | 符合仅 local 预期 |

### 4.5 SSE 流并发

| 指标 | 结果 |
|---|---|
| 容器分布 | local 20 / w1 20 |
| 并发流 | 400（200/节点） |
| 成功状态 | 400 × 200 |
| 峰值 activeStreams | local 200 / w1 200 |
| 网关 fd 峰值 | 1023 |
| 流结束后 fd | 28 |
| 流结束后 activeStreams | local 0 / w1 0 |
| 错误 | 0 |

说明：每节点连接池 600，400 条流共占用 400 条 Docker 连接（200/节点），其余留给普通 API。本次流的输出很小（每流 10 行），高输出/慢客户端场景未覆盖。

## 5. 历史对比

以下对比来自同一环境改造前后，测试参数不完全相同，仅作方向性参考。

| 项目 | 改造前 | 改造后 |
|---|---|---|
| 远程创建 p50 | 约 9.7s（40 并发、旧镜像） | 0.66s（60 并发、新镜像） |
| 双节点创建分布 | local 24 / w1 16（40 并发） | local 30 / w1 29（60 并发） |
| 单节点 30 上限 | 40 个可全部落 local（穿透） | 严格 30，超出返回 503 |
| 镜像 /workspace | 173MB（含 170MB Go 缓存） | 2.7MB |

改造内容：

- 镜像瘦身：删除构建 yq 产生的 Go build cache。
- 调度：创建即占位，每节点 assigned/inFlight，5s 对账。
- 工作区：远程命名卷，copy-up 从 173MB 降到 2.7MB。

## 6. 分析

1. **容量提升明确**：单节点上限 30 被严格执行，双节点可用 60；60 个并发请求得到 59 成功、1 个预期 503。
2. **调度分布合理**：各场景均接近 50/50，说明按节点 assigned+inFlight 评分有效。
3. **CPU 型任务近线性**：1.94x 加速，8C + 8C 符合预期；加节点对 CPU 密集任务有效。
4. **轻量 exec 无提升**：单/双节点吞吐几乎相同，说明瓶颈在网关请求处理、Docker exec 往返和客户端连接方式，不在节点 CPU。
5. **创建延迟受容量保护影响**：双节点 p95 略高于单节点，因为单节点有 30 个请求快速失败；成功请求延迟仍在 0.7s 量级。

## 7. 网关链路连接复用评估

> 本节为配置与代码层面的分析，相关链路未纳入本次压测数据。

### 7.1 现状

| 链路 | 当前实现 | 判断 |
|---|---|---|
| 客户端 -> 网关 | Tomcat/HTTP keep-alive 默认开启；是否复用取决于调用方 | 本次压测客户端每次新建 TCP，QPS 为下界 |
| 网关 -> Docker 节点 | docker-java Zerodep，每节点一个客户端；maxConnections=600（可配置），连接超时 10s，响应超时 60s | 有连接池；200 条 SSE 流占用 200 条，剩余 400 条给普通 API；每个 exec 约 4 次 Docker API 调用 |
| 网关 -> 容器 HTTP 反代 | JDK HttpClient 单例，默认 HTTP/2，未显式配置连接池 | 依赖 JDK 内部池与上游 keep-alive；上游通常是 HTTP/1.1 |
| SSE exec | 每条流独占 HTTP 连接，无法复用 | 当前上限 200/节点；400 条并发已验证，结束后连接释放 |
| 文件传输 | Docker archive 流式 | 小文件可通过连接复用受益，大文件受带宽限制 |

### 7.2 可选优化

| 优化 | 做法 | 预期收益 | 风险/成本 |
|---|---|---|---|
| 客户端连接池 | 调用方使用持久连接/连接池，保持 keep-alive | 轻量 get/exec 的 QPS 可明显提升，降低 TCP/TLS 开销 | 纯客户端改动，服务端零改动 |
| Docker 客户端池调优 | 配置总连接/每路由连接、空闲回收、keep-alive | 高并发 exec/list/create 时减少排队 | 需 docker-java 配置支持；过大可能压垮 dockerd |
| 反代 HttpClient 调整 | 明确 HTTP/1.1、连接池大小、keep-alive 空闲时间 | 提升 /proxy 吞吐，降低 p99 | 需改 ContainerController 的 HttpClient 构造并回归 |
| 减少 exec 往返 | 评估合并 exec create/start/inspect 或复用 exec 会话 | 降低每次 exec 固定开销 | Docker API 限制；安全和复杂度高，不建议优先做 |
| 多网关 | 多实例 + 共享端口池/幂等/限流 | 提升网关总 QPS 与可用性 | 工程量大，需共享状态 |

### 7.3 优先级建议

1. 先让调用方使用连接池/keep-alive；这是轻量 exec QPS 的第一瓶颈，服务端零改动。
2. Docker 连接池当前 600/节点、200 流/节点，剩余 400 条给普通 API；若继续提高流上限，按流数 x 3 同步提高连接池。
3. 若 /proxy 占比高，再优化反代 HttpClient 的 HTTP 版本和连接池。
4. 多网关主要用于可用性和极高 QPS，不是当前 CPU 瓶颈；不建议优先做。

## 8. 风险、限制与未覆盖项

- 本次仅 2 个 8C 节点，未验证 3 节点以上线性度。
- CPU 压测为短时突发（约 4-7 秒），未做长时间 soak。
- 单节点基线通过 iptables 阻断模拟，不是真实关机；w1 上业务容器会有短暂不可访问。
- 压测客户端未使用连接池，轻量 QPS 是下界。
- w1 上存在业务容器（mysql、xxl-job 等），容量与 CPU 结果受其背景负载影响。
- 未覆盖文件上传/下载、HTTP 反代专项压测。
- SSE 仅验证 400 条低输出流；高输出、慢客户端、长时间保持未覆盖。
- 200 流/节点是高并发配置，生产需持续观察网关内存、fd 和 Docker 连接池等待。

---

## 9. 建议

1. 容量规划按每节点 30 个容器线性扩容；CPU 型任务可放心加节点。
2. 轻量 API/exec 的 QPS 优化先从调用方连接复用开始，再考虑 Docker 客户端池。
3. 后续接入更多节点时保持同规格，避免选路只看容器数造成不均。
4. 监控重点：每节点 assigned/运行容器数、Docker 连接池租用/等待、网关 p99、503 比例、SSE activeStreams。
5. 流式容量：当前 200/节点、连接池 600；提高流上限时同步提高连接池并压测高输出场景。
6. 需要更高可用性时再规划多网关，并同步设计共享端口池、幂等和限流状态。
